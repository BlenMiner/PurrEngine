# Tide: Agent Guide

Rules and decisions for anyone, human or AI agent, working on Tide. Only agreed decisions go in this file. Open questions stay out until they're decided.

## Working agreement

- The project owner is the lead programmer and writes most of the code.
- Agents help with specific, scoped tasks. Do what was asked. Don't widen scope, scaffold systems, or refactor nearby code unless asked.
- If it's unclear whether the owner wants code or discussion, ask.
- **Exception: Claude owns the transpiler.** The owner decides the language design (what it should do, its syntax and semantics). Claude implements and maintains the transpiler, including its tests and build integration, and proposes designs for the owner to approve.
- The contract between the two sides is the C the transpiler generates and the engine runtime functions that code calls. The owner writes the runtime. Any runtime function the generated code needs is agreed on before either side depends on it.

## What Tide is

A networking-first game engine:

- The simulation is deterministic and uses floats, not fixed point, on supported hardware.
- User code and the engine's built-in systems are written in a custom language that compiles to native code.
- An ECS runs systems on multiple threads automatically. Data dependencies come from the ECS and the language, so users never have to think about threads.
- Graphics work is kept to a minimum. Rendering is not the focus.

## Platforms

- The main targets are desktop and consoles.
- The web (WebAssembly, rendering with WebGL) is actively supported and tested, not an afterthought. Changes must keep the web build working.
- Determinism holds on every platform, the web included, so web and desktop players can share one simulation.

## Rendering and platform

- raylib handles windows, input and rendering for now. The web build renders with WebGL 2, through our own JavaScript (see Web builds).
- Rendering stays disconnected from the simulation, so it can be replaced later (for example for consoles):
  - The simulation never includes raylib or any platform header.
  - The view reads the world and draws it. It never writes simulation state.
  - The platform layer's only link to the simulation is filling `Devices`.
  - Game code and raylib never share a source file: generated headers name types after the game's components (`Transform`), and raylib defines many of the same names. Hosts include `tide/platform.h`, which doesn't include raylib, and `tide_platform` keeps raylib private.
- `tide/run.h` is the standard host: `tide_run(&(tide_run_desc){.title = "...", .argc = argc, .argv = argv})` opens a window and runs the game in a session (`tide/session.h`), sampling this machine's input from the devices once per tick it runs, and draws its views and their GUI. When `Main` is the match's, it starts at once, and opens it with `--host [port]`, or joins another with `--join code` (a room's) or `--connect address`. This machine's player joins before the first tick. A game needs no other C. Its loop is in `tide/host.h`, which runs a game through a table of its functions (`tide_host_game`), so that `tide run` can swap builds (see Hot reloading).
- Views are written in Tide (`view` declarations). Their `Draw` calls record commands into a renderer-agnostic draw list (`tide/draw.h`), which grows as it needs, with no limit but memory. The platform layer renders the list (`tide_platform_draw`), so replacing raylib only means rewriting that function. Drawing a lot has to stay cheap: shapes (rects, circles, their outlines and lines) go to the GPU as instances of one quad, each its shape in window pixels, so a run of them between text and clears is one draw call (`platform/src/platform.c`); text goes through raylib. `tide_platform_draw --bench` (`?bench` on the web) times frames of 65,536 shapes. `tide_run_desc.stats` (`STATS`, `tide run --stats`) shows the frame rate, ping, bandwidth (sessions count the bytes of their datagrams over networks, not loopback: `tide_session_status.sent_bytes` and `received_bytes`), tick, entity count and the threads ticks run on (`tide_platform_jobs`) in the bottom right corner.
- The GUI (`GUI` and `GUILayout` in Tide, `tide/gui.h` in C) is immediate mode, like Draw, and local: widgets change local state, never the match. It records into a list of its own, which `tide_gui_end` adds after the world's, in pixels (from the top left, y down), so widgets keep their size when the window changes. It measures text with the platform's font (`tide_platform_measure_text`). Views read the devices through it (`Devices` in Tide): `tide_gui_begin` works out what changed since last frame and hides what the GUI uses.

## Tech stack

- The engine is written in C and compiled with clang on every platform.
- The custom language transpiles to C.
- User code and engine code are compiled and optimized together, so calls between them cost nothing.

## Building

Requires CMake 3.25+, Ninja, and clang. The build finds clang automatically, checking `$LLVM_ROOT/bin`, then a standalone LLVM install, then `PATH`, then Visual Studio's bundled clang. This works with any CMake invocation, not just the presets.

- Configure, build and test in one step: `cmake --workflow --preset debug`
- Build only: `cmake --build --preset debug`
- Run tests: `ctest --preset debug`, or run `build/debug/bin/tide_tests [name-filter]` directly
- Run the sandbox: `build/debug/bin/sandbox`
- Run the demo: `build/debug/bin/demo`, or open `build/web-release/bin/demo.html` in a browser after a web build. Two players: `demo --host` in one window and `demo --connect 127.0.0.1` in another (or another machine's address).
- Run a benchmark: `build/release/bin/bench_sand` (see Benchmarks).

There are two presets for everyday work. `debug` has no optimization. `release` is optimized and keeps debug info for profiling. Web builds, MinGW builds and the package have their own (see below).

Warnings are errors, wherever they come from, and one that's already there gets fixed, never left alone:

- The compiler's: our C builds with `-Werror` (`cmake/TideFlags.cmake`). Third-party code (raylib, LLVM's headers) is built with its warnings off.
- tidec's, in the games `tide_add_game` builds (`cmake/run_tidec.cmake`). A test of what tidec generates for a program it warns about lists those warnings after `WARNINGS`, and the build checks they're there.
- The browser's, in web tests: test pages set `Tide.checkGL`, so a GL error stops the program and names the call (`platform/web/tide.js`), where WebGL would only warn in the console. It checks every call, which is too slow for pages that ship.

Every native build also copies the language server to `build/tools/tidels`, the fixed path editors run: the VS Code extension and the JetBrains plugin use it when the open folder is this repo (see `tools/`). On Windows, a build replaces the server while an editor still runs the old one: the running file is renamed aside and deleted by a later build.

The first configure downloads raylib (see `cmake/Raylib.cmake`). Configure with `-DTIDE_PLATFORM=OFF` to build without the platform layer and the demo, for example offline.

### Web builds

- The `web-debug` and `web-release` presets build everything as WebAssembly with clang's own wasm target and wasi-libc, not Emscripten: `cmake --workflow --preset web-debug` (see `cmake/wasi-toolchain.cmake`). They need clang with `wasm-ld` (LLVM's releases have it; on Linux, the distribution's `lld`) and Node. wasi-sdk's C library is downloaded once into `build/wasi-sdk-<version>`, pinned.
- Tests run under Node's WASI through CTest (`cmake/run_wasi.mjs`), so the determinism hashes cover exactly what ships. Games generate their C with a native tidec, which web builds build first in `<build>/host` (`cmake/HostTidec.cmake`).
- In the browser, `platform/web/tide.js` runs the program: the canvas, input and frame loop (`platform/web/tide_web.h`), the OpenGL ES 3 functions rlgl calls on WebGL 2, and the few WASI functions wasi-libc needs. raylib gets our platform backend (`platform/web/raylib/rcore_web_tide.c`), patched into its `rcore.c` by `cmake/Raylib.cmake`. A web page is one self-contained `.html` with the program inside (`cmake/web_page.mjs`, or tide).
- Web builds have threads: the target is `wasm32-wasip1-threads`, and programs import their memory (`--import-memory`, up to 4 GiB). A cross-origin isolated page (served with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`) makes it shared, and each thread the program starts (`pthread_create`, through wasi-threads' `thread-spawn`) is a worker running the same program on it (`tide.js`). Browsers won't share memory with other pages, so there the page gives the program memory of its own, changing the flag in its import to match, and it runs on one thread (`tide_web_threads` says 1), with the same results. The page's main thread can never block, so the web's pool (`platform/src/jobs.c`) only spins there and wakes workers with atomics, and wasi-libc's `malloc` spins too (`sched_yield`). Browsers won't take views of shared memory for some calls (`TextDecoder`, `crypto.getRandomValues`, data channels): copy out first. When one thread grows the memory, V8 (Node 24's, at least) lets the others use what was added only once they hear of it, so memcpy and memset into memory another thread's growth made trap until then: engine code that runs on threads allocates with `tide_alloc`, `tide_alloc_zeroed` and `tide_realloc` (`tide/page.h`), never calloc or realloc, and calls `tide_memory_sync` where it picks up what other threads made (tasks, settling, a system's finish, the end of a tick's threads). The engine's `sbrk` notes how far the memory grew, so that's a comparison until it did. A worker's crash ends the program under Node (`run_wasi.mjs`), where it would leave the main thread spinning. The pool makes its workers the first time a tick has enough work for them (about three times desktop's threshold, since waking a worker costs more), as each costs a page far more than a thread does. Node runs tests the same way (`cmake/run_wasi.mjs`, with `worker_threads`), and `tide_platform_web_threads` ticks on threads in a cross-origin isolated page in headless Chrome, against one thread. `tide run --web` serves its page isolated; pages made to ship need a host that sends those headers (itch.io's SharedArrayBuffer option does) to run on threads.
- Games keep running where nobody sees them, so a match goes on for the other players when its host switches tabs or minimizes. Browsers stop a hidden page's animation frames and slow its timers to about one a second, so while the page is hidden, frames come from a worker's timers (`tide.js`). Desktop windows keep running while minimized (`FLAG_WINDOW_ALWAYS_RUN`; raylib would stop the loop), waiting between frames on GLFW's events (`glfwWaitEventsTimeout`), so a window restored or closed goes on at once. Either way, each frame comes when the host says it next has work (`tide_platform_next_frame`), which for `tide/host.h` is its match's next tick (`tide_session_until_tick`), so frames follow the tick rate; a host that doesn't say gets 60 a second. Neither draws meanwhile (`tide_platform_draw`). `tide_platform_web_rooms` hides the host's page past the players' timeout, throttled as browsers throttle it, and the match has to go on, with frames at its tick rate.
- `tide_platform_web_rooms` puts two players in a room: a relay on this machine (`relay/`), and WebRTC between two frames of one page in headless Chrome or Edge, in real time rather than the other web tests' virtual time (`platform/tests/web_rooms.mjs`); `tide_platform_web_rooms_handover` puts three there, whose host leaves, to check host migration. With `TIDE_RELAY` set, like `wss://relay.tide-engine.dev`, that script checks a deployed relay instead, and with `TIDE_ICE_POLICY=relay` too, its TURN (every packet through it). The relay's own tests run wherever there's Node (`node --test relay/relay.test.mjs`).
- Desktop rooms have tests of their own in every native build:
  - `tide_platform_rtc` checks each piece of `platform/src/rtc/` (crypto against the RFCs' values).
  - `tide_platform_rtc_vectors` (`platform/tests/rtc_vectors.mjs`) checks the crypto against Node's (OpenSSL's) on random inputs every run, and Node checks our signatures.
  - `tide_platform_rtc_fuzz` feeds everything that reads other machines' messages (JSON, SDP, STUN and TURN, certificates, DTLS, SCTP, WebSocket frames) real messages broken at random, with checksums and signatures made right again. Configure with `-DTIDE_SANITIZE=ON` (Linux and macOS) for AddressSanitizer and UndefinedBehaviorSanitizer, and give it more rounds: `tide_platform_rtc_fuzz 20000 <seed>`.
  - `tide_platform_rooms` (`platform/tests/rooms.mjs`) puts two desktop players in a match through a relay on this machine, and three in one whose host leaves (host migration), then each browser it finds (headless Chrome or Edge, and Firefox) in a desktop room and a desktop player in that browser's room, with the browser showing its address and hiding it. The same `TIDE_RELAY` (like `wss://relay.tide-engine.dev`) and `TIDE_ICE_POLICY` check a deployed relay and its TURN.
  - On a relay on this machine, desktop players' sockets stay on loopback (`TIDE_RTC_LOCAL`), so Windows' firewall has nothing to ask; Firefox on Windows offers no loopback candidates, so its cases use ordinary sockets. `TIDE_RTC_DEBUG=1` has the desktop side say what it does.
  - A browser's `--user-data-dir` (or Firefox's `--profile`) must be an absolute folder that exists, or the browser shows a dialog, even headless. Firefox needs `--wait-for-browser`, or stopping it leaves the browser running.
  - Chrome is stopped by asking it to close (`Browser.close` on `--remote-debugging-pipe`): killing its processes from outside can miss one it starts again meanwhile, which keeps the browser from going. Each case starts once the last browser is gone, and its deadlines start once the page says it loaded, since a browser's first start on a fresh machine (CI) can take most of a minute.
- Before finishing a change, the native and web test suites must both pass.

### MinGW builds

- On Windows, the `mingw-release` preset builds everything for the MinGW-w64 target (`x86_64-w64-windows-gnu`, with the UCRT), which tide builds Windows games for (see Packaging and releases): `cmake --workflow --preset mingw-release`. Everyday Windows builds keep Visual Studio's target.
- Its headers, C runtime and compiler runtime come from llvm-mingw, downloaded once into `build/llvm-mingw-<version>`, pinned (`cmake/mingw-toolchain.cmake`). clang is the usual one, linking with lld.

### Cross-platform determinism tests

- `tests/test_crossplatform.c` and `compiler/tests/e2e/crossplatform` hash the exact bits of math results and of a full simulation. The hashes must be identical on every platform and in every configuration.
- If math or generated code changes the results on purpose, update the expected hashes from one platform, then confirm every other platform and configuration agrees.
- Test code must not depend on C's unspecified argument evaluation order: clang goes right to left on Windows and left to right on WebAssembly. Draw random inputs into locals first.
- The demo's smoke test (`demo --smoke`, or `demo.html?smoke`) plays a scripted session through the real platform layer. It checks a hash of the simulation (`SMOKE_HASH` in `demo/main.c`, the same on every platform) and pixels read back from the renderer. The native presets run it in a hidden window, so they need a desktop session with OpenGL; so does `tide_platform_draw`, which checks the renderer's pixels. Native tests like these have the `gpu` label, which CI leaves out (`ctest -LE gpu`), as its runners have no GPU. The web presets run it in headless Chrome or Edge on the browser's software WebGL, and skip it if neither browser is found.

### Benchmarks

- `bench/` holds games that stress the engine, played by bots, as targets for what a general engine has to handle: `sand` (falling sand and water that every player paints into at once) and `gallery` (every player has a big canvas of their own, and players keep joining). A voxel world, endless, with blocks placed and broken, joins them once the engine can hold one.
- Each is a program, `bench_<name>` (`--help` lists its options), on a harness of its own (`bench/bench.h`): a dedicated server and bots, each a client of its own on the loopback network, with latency and loss, in made-up time, so a run goes as fast as the machine can take it and repeats exactly. It reports each machine's update times, what they spent simulating, hashing, snapshotting and packing worlds (through the game's `tide_game`), what each machine sends, how long joins take, and the world's size.
- Measure with the `release` preset. The machines run one after another, so a run takes about as long as all of them together.
- Tests run each one `--quick`, which fails when a client's world went wrong, a bot couldn't join, or the server's world ends with another hash than the one in `bench/CMakeLists.txt`, which every platform and thread count has to agree on. Timings aren't checked: machines differ too much.
- Sand is a game people play too: `sand` (`sand.html` on the web) is `sand/sand.tide` with `sand/play.tide`, its views, GUI and rooms, and the mouse through the input's `Sample`, which the benchmark's bots don't call. The docs site shows it (see Docs site).
- A benchmark holds its game as the engine can today, and says where that's not how it should be. It changes as the engine does (sand's cells were a list, then a grid that a chunk system stepped on threads, then 2 by 2 blocks that a parallel loop steps), and its expected hash with it.

### Tide programs

`tide_add_game(<target> [SOURCES <file.tide|file.c>...] [HOST <file.c>...] [NAME <name>] [TITLE <title>] [STATS] [WARNINGS <text>...])` builds a game as the program `<target>` (see `cmake/Tide.cmake`):

- The game is every `.tide` file in the current source folder and its subfolders; the next build picks up new files. `SOURCES` lists the files instead, for tests and folders that hold several games.
- The game's C (its `extern` functions') is every `.c` file there but the `HOST` ones and those in hidden folders or `build/`, or the `.c` files in `SOURCES`. Unlike `tide`, it doesn't pick up prebuilt libraries.
- Without `HOST`, the game is the whole program and needs no C: a generated `main` runs it in a window through `tide/run.h`. On the web it's `<target>.html`.
- With `HOST`, those C files are the program (tests, the demo's smoke test, custom hosts). They include `<name>.h`, where `NAME` defaults to `<target>`.
- `tidec` compiles all the files together, in order of their paths. The generated files regenerate whenever a `.tide` file or `tidec` changes.
- A warning from `tidec` fails the build, unless part of its text is listed after `WARNINGS`; each of those has to be there (see Building).
- `<target>_schedule` is a build target that prints the game's schedule: which systems can run at the same time, and why the others wait.
- Every game's files are listed in `build/tools/games.txt`, one `<game>\t<path>` per line. A path ending in `/` is a folder: every `.tide` file in it and its subfolders, so editors see new files before the next build. `tidels` reads it, and the one in `build/tools/` of any folder open in the editor, to analyze a game's files together, in `tidec`'s order. A file in no game belongs to the open folder it's in, as `tide run` would build that folder, unless a manifest lists games in that folder: then it's analyzed alone.

The generated header is the API between the game and the host. Namespaced declarations have their namespace in their C name: `Combat.Health` is `Combat_Health`, read with `tide_get_Combat_Health`.

- `tide_world`: the whole simulation state. Its data is in pages it shares with its snapshots (see ECS and simulation state), so a world starts zeroed (`{0}`, static or `calloc`), copying the struct isn't a snapshot (`tide_world_copy` is), and `tide_world_free(w)` lets it go. When fields hold text or lists, it has a `heap` they're kept in; hosts read a text field with `tide_text_read(&w->heap, field)`.
- `tide_world_init(w, dt)`: clears the world, sets `Time.dt` and singleton defaults, and loads the `Main` scene if it's the match's.
- `TIDE_MAIN_IS_LOCAL` is defined when `Main` is a local scene: the program starts outside any match.
- `tide_world_tick(w)`: runs every system once, then applies structural changes. With no scene left, it loads `Main` again if it's the match's; `tide_frame` does the same for a local `Main`.
- `tide_world_ended(w)`: whether the match is over: its last scene unloaded and `Main` is local, so it can't come back. The server stops ticking there and tells every player, who go offline with `TIDE_DISCONNECT_ENDED` (`Ended` in Tide).
- `tide_local`: this machine's local state, outside every world. `tide_local_init(local)` clears it and sets its singletons' defaults.
- `tide_frame(w, previous, alpha, local, draw, gui)`: runs every view once, adding their Draw calls to a `tide_draw_list` and their widgets to a `tide_gui`, then applies the local changes they made. Views see the match's floats blended from `previous`, the tick before `w`, by `alpha` (0 to 1), so they're smooth at any tick rate; `tide_session_view` gives all three. Pass NULL and 1 to draw `w` as it is. Call it once per frame, after `tide_draw_reset(draw)` and `tide_gui_begin(gui, devices, tide_platform_screen_size(), tide_platform_measure_text)`, then `tide_gui_end(gui, draw)` and render the list with `tide_platform_draw(draw)`. Outside a match `w` is NULL, and views that read the match don't run. A zeroed `tide_gui` is ready to use.
- `tide_get_<Component>(w, entity)`: a component of an entity to change, or `NULL`; `tide_read_<Component>` only to read, which leaves shared pages shared. A local component's take the `tide_local`. `TIDE_AT(w, arch0_Body, Body, row)` and `TIDE_ENTITY_AT(w, arch0_Body, row)` read an archetype's rows, for tests and tools.
- `tide_world_player_joined(w, player)` and `tide_world_player_left(w, player)`: send `PlayerJoined` and `PlayerLeft`, handled at the end of the next tick. Every machine calls them before the same tick.
- `tide_world_entity_count(w)` and `tide_world_print(w)`: for debugging.
- `tide_world_copy(to, from)` and `tide_world_hash(w)`: snapshots and state hashes between ticks. `tide_world_pack(w, out, capacity)` and `tide_world_unpack(w, data, size)`: the world as bytes, which hot reloading carries over; the same for the local state (`tide_local_pack`, `tide_local_unpack`, `tide_local_free`).
- `tide_world_pack_delta(w, base, need, need_size, &size)` and `tide_world_unpack_delta(w, base, data, size)`: the world as a delta (`tide/delta.h`), which sessions send: page by page, what differs from `base` (a world the receiver has too: changed pages go XOR'd with the base's), or from the receiver's own world, which lacks the pages `need` says, or the whole world. `tide_world_hash_pages(w, &size)` lists the pages' hashes, and `tide_world_need_pages(base, hashes, size, out, capacity)` says which of them a world lacks. Unpacking shares the base's pages that are the same and checks the world's hash. Storage a world gains (like the tables of tasks) goes in all of these as it does in packing, copying and hashing: what's left out stays in the struct's bytes, pointers and all.
- `tide_world_start(w, dt, start)`: `tide_world_init`, starting the match in the scene `start` names (`tide_start`, from `Session.Start`), or `Main` for NULL.
- `tide_game_api`: the game as sessions run it (`tide_game` in `tide/session.h`): the world's size and functions, the input packed for the network, and its settings (`settings { ... }`): `tick_rate` and `title`, 0 and NULL where it sets none. They're in the generated `.c`, so they don't change `tide_game`'s hash. A session whose desc leaves `tick_rate` at 0 starts its matches at the game's rate, or 60; `tide_run_desc`'s `title` (`TITLE`, `--title`) goes over the game's, and `game_name` stands in when neither says.
- Local code's requests of the session (`Session.Start` and the like) wait in the local state: `tide_local_take_request(local, &request, &start)` takes them, in order. `Clipboard.Copy` goes the same way, as `TIDE_REQUEST_COPY`, after them, and hosts put its text on the clipboard (`tide_platform_copy`). Pasting is the platform's: Ctrl+V (Cmd+V) types the clipboard's text into `tide_devices.text`, from raylib's clipboard on desktop and the browser's `paste` event on the web. Hosts tell local code where it stands with `tide_local_set_session(local, state, player, ping, server, open, room)` (`open` from `tide_session_status`, the room from `tide_platform_room_code`, `""` while the match is closed), `tide_local_connected(local)` and `tide_local_disconnected(local, reason, message)` (a kick's message, from `tide_session_event`). Before each `tide_frame`, hosts give the frame's length with `tide_local_frame_time(local, seconds)` (`tide_host_game.frame_time`), which local tasks' `Wait.Seconds` counts down. `gone.message`, like `Session.room`, is kept beside the local state rather than in a field, so neither costs a game a heap.
- If the game has an input (it declares one, or systems take `Devices`), `TIDE_HAS_INPUT` is defined and `tide_input` names its type. `tide_input_sample(devices, local)` runs the input's `Sample` on the client, with this machine's local state: give it a copy of the devices that `tide_gui_hide(gui, &copy)` took what the GUI is using out of, then call `tide_devices_consume(devices)` on the real ones. The input holds what match code reads of the devices (`tide_dev`), everything else zero. `tide_world_set_input(w, player, input)` sets a player's input for the next tick, and `tide_world_set_server_input(w, input)` the server's, which entities without an owner read. Both repair NaN and infinite floats, apply the fields' `[Clamp]`, `[Min]` and `[Max]`, then run the input's `Sanitize`, if it has one.

## Packaging and releases

Users get Tide as the `tide` command, not this repo: see README.md.

- `tide run [--host [port] | --join code | --connect address]`, `tide build [--release] [--web]`, `tide schedule`, `tide editors`, `tide upgrade` and `tide version` (`compiler/cli/`, owned by Claude). It runs tidec's front end in-process, compiles the generated C and the engine's sources with the determinism flags (as separate files, like the CMake build), and links the prebuilt platform layer. `tide run` reloads the game as its files change (see Hot reloading).
- Packages have clang and lld built into tide (`TIDE_EMBED_LLVM`, `compiler/cli/llvm/cc.cpp`), so users need no compiler: `tide cc` is clang, whose compiles run in tide's process and whose links go to lld in it. tide links the static libraries of LLVM's own release, downloaded once into `build/llvm-<version>` and pinned (`cmake/LLVM.cmake`, which also builds the zlib, zstd and libxml2 they were built with; unpacking needs the `zstd` program). macOS's release holds them as LLVM bitcode, so tide links there with that release's lld. Builds of this repo without the option use an installed clang (`--web` needs `wasm-ld` next to it).
- The package brings the C library for web games (wasi-libc) and for Windows games, which build for MinGW-w64 (see MinGW builds): Microsoft's C runtime can't ship with tide, and the UCRT is part of Windows, so players need nothing else. Linux games use the system's C development files, and macOS games the SDK of Apple's command-line tools (tide sets `SDKROOT`).
- A game is a folder of `.tide` files. tide keeps its work in `<folder>/.tide/` (hidden on Windows too, and it ignores itself in git) and puts `tide build` output in `<folder>/build/`.
- A game's C is in its folder too, outside hidden folders and `build/`: every `.c` file compiles with the game's flags (each again only when it, a header there or the flags change), and every library (`.a`, `.lib`, `.so`, `.dll`, `.dylib`) links when its contents say it was built for the target's platform and CPU (`compiler/cli/libraries.c`), since `.a` is every platform's. `.so`, `.dll` and `.dylib` files are copied next to the program, and `.so`/`.dylib` ones found there through its rpath; a `.dll` links through its import library. Web programs link with undefined functions allowed (the page provides GL's), so a web build fails when one of the game's extern functions is among its imports.
- The package is everything installed as the `tide` component: `bin/` (tide, tidels), `include/`, `src/engine/`, `lib/native/` and `lib/web/` (the prebuilt platform layer and raylib), `wasi/` (wasi-libc and the compiler runtime for wasm), `mingw/` (on Windows: MinGW-w64's headers, C runtime and compiler runtime), `lib/clang/` (clang's own headers), `web/` (the page and `tide.js`), `editors/` and `VERSION`. It comes from the `package` preset (clang and lld built in, static C runtime on Windows), the `web-package` preset and, on Windows, the `mingw-release` preset, put together by `cmake -DNAME=tide-windows-x64 -P cmake/package.cmake` into `build/dist`. Anything tide needs at build time must be installed into the package; a game build can't see this repo. The same goes for `tidels`, which reads the engine headers from the package's `include/`. Nothing else goes in: games are C, built for this machine's CPU and the web, so the package leaves out C++ headers, Windows' interface definitions (`.idl`) and type libraries, and clang's headers for other CPUs, GPUs and the runtimes it doesn't ship (`cmake/LLVM.cmake`, `platform/CMakeLists.txt`). Every C header of the C libraries stays, since a game's C can include any of them.
- `editors/tide.vsix` is the VS Code extension (`tools/tide-vscode`), for VS Code, Cursor, VSCodium and Windsurf. Only the `package` preset builds it (`TIDE_EDITOR_EXTENSIONS`), since it needs Node's npm. The installers run `tide editors`, which installs it into every one of those editors it finds, and `tide upgrade` updates it in the editors that have it.
- The JetBrains plugin (`tools/tide-jetbrains`, Gradle and Java; on Marketplace as `io.github.blenminer.tide`) isn't in the package: CI builds it and checks it with the plugin verifier on every push, attaches it to each release, and publishes stable releases to JetBrains Marketplace with the `JETBRAINS_MARKETPLACE_TOKEN` secret. Marketplace installs LSP4IJ, which it needs, along with it.
- Users install with `install.ps1` or `install.sh` into `%LOCALAPPDATA%\Tide` or `~/.tide`, with `bin` on `PATH`, and `tide upgrade` replaces the installation from GitHub Releases. It checks each download against the release's `SHA256SUMS`, and renames running programs aside instead of overwriting them. Once a day, tide says when a newer version is out. tide and the installers pick a channel's highest version by semantic versioning (`compiler/cli/release.c`), never the last one published, and stable also asks GitHub for its latest release, which nightly ones push out of the list. `tide upgrade` only goes forward, except to an exact `--version` or when switching channels. Builds made from this repo are versioned `<VERSION>-dev` and never look for updates.
- `.github/workflows/build.yml` tests and packages Windows, Linux and macOS on every push and pull request (macOS doesn't hold back releases yet), and tests the MinGW target on Windows. Windows and Linux build with the LLVM tide's built-in clang comes from (`TIDE_LLVM_VERSION`): LLVM's own release on Windows, and LLVM's apt packages of that major version on Linux. macOS builds native code with Apple's clang and web code with Homebrew's LLVM. Pushes to `dev` publish nightly pre-releases (`0.2.0-nightly.3`); pushes to `release` publish stable releases, and semantic-release commits the new `VERSION` there. Native tests that need a GPU (label `gpu`) are skipped in CI, which has none.
- Versions come from conventional commits (`.releaserc.json`): `fix:` is a patch, `feat:` a minor version. While the version starts with 0, breaking changes (`feat!:`) are minor versions too, and we avoid them until 1.0 anyway.

### Hot reloading

It's for quick iteration, and only under `tide run`, native and web: `tide build` output has none of it.

- `tide run` builds the game as a library (`game-<n>.dll`, `.so` or `.dylib`) and a small host that loads it (`tide_host_run_library`, in `platform/src/reload.c`). tide watches the game's `.tide` files, and its C files, headers and libraries, and builds again once a change has settled. The game's C is part of its library, so the state C keeps starts over at each reload. Each build is linked under another name and renamed into place when it's whole; between two frames, the host swaps in the newest.
- A build with the same data layout keeps the match and the local state where they are (`tide_session_set_game`). The layout is `tide_game`'s hash: the generated header but for its first line.
- A build with another layout gets the match and the local state carried over by name (`tide/migrate.h`, `tide_session_migrate`). Keep as much state as possible, and when a big change breaks it, starting over is fine. No attribute for renamed fields, like Unity's `[FormerlySerializedAs]`, and no save files. The rules:
  - Fields of the same name keep their values. `int` to `float` and int vectors to float vectors of the same size convert, as Tide converts them implicitly, and enums keep their member by name. Other fields, and new ones, get their declared default; new text and lists start empty. A changed default doesn't touch existing values.
  - Entities keep their IDs. Without a removed component, an entity goes to the storage for the rest of its components. It's dropped when there's none.
  - A world whose scene is gone starts over.
  - The host says what didn't carry over: fields reset and entities dropped.
- tidec describes a game's layout for this only when asked (`--layout`, `codegen_options.layout`, `tide_add_game(... LAYOUT)`): `tide_game_layout` in the generated `.c`, not the header, so `tide_game`'s hash doesn't change. The migration is in the platform layer's static library (`platform/src/migrate.c`), so only programs that call it link it.
- In a match, the server's machine carries its world over, and its own player takes that world. A client of another machine carries its last verified world over, and the server sends what it lacks if it comes out different. Inputs sent for ticks to come are dropped: players' last inputs stand in until new ones arrive.
- A waiting task carries over to a build where its code and its frame's layout are the same: each table of tasks in `tide_game_layout` is named with a fingerprint of both, and the header says each one's code, so a change to async code changes the layout. Other waiting tasks are dropped, and the host says how many. A world's task order and the local world's frame count go on.
- A build that fails leaves the game running its last one. `r` and Enter in tide's terminal starts the game over (through a `restart` file in the run's folder). The host says what each reload did, so under `tide run` it's a console program even with `--release`.
- A game started with `--join` or `--connect` joins again a second after its match ends without it leaving: when the server starts over, or still runs an older layout.
- Each run has its own folder, `.tide/<configuration>/run/<tide's process ID>`, so a server and a client run from one folder never build over each other. It keeps the last two builds, and it's deleted when the run ends, or by a later run once its tide is gone.
- A game's library has its own copy of the engine code it uses. So everything the host and the library share is data: worlds and local state (with their pages, from the C library's heap, which every build of the game shares), devices, the draw list and the GUI. The library frees its scratch area before it's unloaded (`tide_host_game.unload`).
- On Linux, a library's objects are compiled with `-fPIC`. The engine's are kept apart in `engine-pic`, so running and building don't rebuild each other's.
- On the web, each build is a WebAssembly program of its own. `tide run --web` serves the page on 127.0.0.1 (`compiler/cli/serve.c`), opens it (unless `--no-open`), and keeps running until it's stopped. The editors run it with `--no-open` and show the page themselves, at the address tide prints (`tide: the game is at ...`): VS Code's **Tide: Run on the Web** in its browser, and the JetBrains plugin's Tide run configurations in the Tide Game tool window. The page asks tide for the newest build 4 times a second (`/build`: the build and restart numbers; `/game-<n>.wasm`).
- The page starts each new build in the running one's place (`platform/web/tide.js`, between its `tide run` markers): it asks the running one for its state (`tide_reload_save`), deletes its WebGL objects, and starts the new one, which carries that state over (`tide_host_run_web` in `platform/src/reload.c`). The state is the old layout, packed with offsets for pointers (`tide_layout_pack`), the server's world and the local state as bytes (`tide_world_pack`, `tide_local_pack`), and the GUI. The new session goes on from the world with this machine's player in it already (`tide_session_start_from`), so there's no second `PlayerJoined`. A room closes at a reload, for now: the new build goes on with the match closed, and the other players drop out.
- Pages made to ship (`tide build --web`, `cmake/web_page.mjs`) leave out the lines between tide.js's `tide run` markers, and web programs only link reload code when tide run's `main.c` calls it.

## Language

The language shares the engine's name, Tide. Its syntax and semantics are specified in `docs/spec.md`. The docs site explains it to users: a change to the language, `tide` or the editors updates the site's pages too (`docs/guide/`, `docs/language/`, `docs/engine/`).

- Derive as much as possible from the language.
- It should be as explicit as our needs require, while staying friendly.
- Dependency trees are static: known at compile time, not discovered at runtime.
- Explicit is the default. Systems declare which components they read and write in their signatures.
- A system's access (which components it reads or writes) is declared separately from its filters (which components an entity must have or lack). Filters don't create data dependencies.
- The language is built around the ECS. It should use syntax sugar to hide the ECS's pain points.
- When nothing else decides a convention (names, axes, units, orderings), follow Unity: Unity.Mathematics for math, the Input System for input. Tide's own rules, such as PascalCase methods, still win.
- Games call C through `extern` functions, and C is trusted: what it does (determinism, state outside the world, thread safety) is the game's responsibility. The language adds no markers or checks for it, and the compiler takes a C call as touching nothing it tracks. tidec declares each one in the generated `.c` from its signature, never in the header (which would change `tide_game`'s hash) and never by including the library's header. Calls to C, and to functions and methods that call it (`decl.calls_c`), are side effects that codegen keeps in source order, as it does spawns. C makes no system wait, and systems that call it split across threads like any other: what C does on several threads at once is the game's to get right.
- Error messages guide the user to the fix: say what's wrong and, whenever it's knowable, what to write instead (a note with the right usage, or "did you mean ..." for a misspelled name).
- Errors are values, never exceptions: a function that can fail says so (`fails`), and the code that calls it handles the error right there (`??`, `is`, `!`, `try`); see `docs/spec.md`, Errors. What can't fail stays forgiving (indexing, arithmetic, text), and failures that come later stay events, like `Disconnected`.
- Async functions and handlers (`async`, `await`, as C#'s, with no `Task<T>`) run as tasks, in the match or in local code: see `docs/spec.md`, Tasks. A task belongs to its world like a component: the match's are in its snapshots, hashes and packed bytes. Match code only waits for what's the same on every machine; a service's answer reaches the match through input.
- No backward compatibility yet: rename and change freely. Old spellings aren't supported; at most, an error points to the new one.

## ECS and simulation state

- The transpiler generates C specific to each game: component structs, archetype storage, per-system dispatch, and the tick. There is no runtime type registry.
- Singletons hold state for the whole world, such as time, RNG and game rules (other ECSs call them resources). There is one of each per world, stored inside it, and systems declare them the same way as components.
- The world is always passed as a pointer, never stored in a global. Several worlds can exist at once, for example predicted and verified copies, several matches on one server, or snapshots.
- The world owns all simulation memory. Components hold offsets into world memory, never pointers. The allocator's state lives in the world too, so a snapshot captures everything.
- Text and lists in fields live in the world's heap (`tide/heap.h`): blocks handed out and reused in a fixed order, so every machine gets the same offsets. Freed memory is zeroed. Generated code says where each text or list it writes is (`where`: the match's, the local world's, or no world's), never the address.
- A world's list whose elements take more than a page keeps them in chunks, heap blocks of a page each, listed in its own block (`tide/list.h`): changing an element copies and hashes its chunk, never the whole list, and growing adds chunks without moving elements. Reading and writing elements is inline. C, which takes a list as its elements side by side, gets a copy of a list in chunks, written back after a `mut` call (`tide_list_flatten`).
- Grids (`Grid2<T>`, `Grid3<T>`, `tide/grid.h`) keep their cells in chunks of 4096 cells (fewer for cells over 4 bytes, so a chunk is never more than a page), a heap block each (its header is cells too, until it's released), listed in the grid's directory: a table by chunk position (by index for a grid sized on every axis, else hashed) and each chunk's record (its position and block). A chunk only exists once a cell in it is set to something other than zero. Grids are fields of components, singletons and scenes only, never copied: tidec keeps them out of locals, structs, events, inputs and functions. Generated code reads and writes cells through a chunk cache per grid type in each function (`tide_grid_cache`, `tide_gc`), so a loop looks each chunk up once rather than at every cell; it holds while the heap's `moves` count (a page copied to be changed, or blocks released) is what it was, so whatever the code calls meanwhile, it never reads stale cells.
- Text and lists that code makes along the way live in a scratch area outside the world, cleared after each system, view and handler runs, and are only ever copied into a world.
- Tasks are state machines tidec makes from async code (`gen_task_resume` in `compiler/src/codegen.c`), as C# does: a resume function per async function or handler and world, which goes on from where its frame says it stopped, until it waits again or ends. A frame is a generated struct: where it stopped, its parameters, its value, the frames of the async functions it awaits (so a task is one frame however deep it awaits, and nothing awaits itself), and a slot for each C local in scope at a wait, which goes in before the task waits and comes back after. No task keeps an address: components and singletons are got again from the task's owner entity each time it goes on. A world keeps its waiting tasks in a `tide_table` (one column: `tide_task`, then the frame) per async function and handler, and goes through them in its task pass, once its tick's changes (or its frame's) are in: those whose time has come go on one at a time, in the order they started, on copies of their frames, as tasks they start may move rows; those whose owner is gone end. A system that starts tasks runs them until they first wait, inside it, so it doesn't split, and waits for systems that start tasks, spawn or change text (`CONFLICT_TASKS`).
- Local state (menus, settings, view state such as particles) belongs to one machine and lives outside every world. It's never sent, rolled back or hashed. The compiler keeps match code from reading it and local code from changing the match (see `docs/spec.md`).
- Generated types (components, singletons, the input and structs) have no padding the compiler adds: tidec writes it out as members, which every value sets to zero, and the generated header checks each type's size (`_Static_assert`). Their bytes only depend on their fields, so snapshots and state hashes can compare memory directly. Input from outside gets its padding cleared along with its other repairs.
- Worlds grow as they need, with no limits but memory (no engine limit stands in for checking inputs: that's the game's): running out of memory ends the program. The one depth that's checked is a chain of events, each sent or spawned by a handler of the one before: an endless one would never stop, so past `TIDE_MAX_CHAIN` (100,000) in one tick the program stops, naming the event. Each queued change records how far down its chain it is. Their data is in pages (`tide/page.h`): each archetype's rows in chunks, each chunk's column a page (`tide/table.h`), the entity table's slots and the heap. A snapshot (`tide_world_copy`) shares the world's pages, and whoever changes a shared page first gets a copy of their own, so a world and its snapshots cost the memory of what's different. Systems make the pages of what they declare `mut` their own, so what nothing changes stays shared.
- Each page keeps the hash of what's in use in it until it changes, so a world's hash (`tide_world_hash`) only reads what changed since the last one. It covers contents, never addresses or capacity, so it's the same on every machine for the same state. The command queue, empty between ticks, isn't shared.
- Chunk sizes come from component sizes, which are the same everywhere: 1 << shift rows each, as many as keep a page to 16 KiB. The first chunk starts with room for 4 rows and grows, so archetypes with a few entities take little memory.

## Performance

- Performance is a top priority. Weigh design choices by their runtime cost.
- Flexible features are fine even if they cost more, as long as the common, fixed path stays fast.
- Friction between engine code and user code should be minimal or non-existent.
- Snapshotting and restoring the full simulation state must be cheap. Rollback depends on it.

## Networking

- Rollback netcode with full server authority. The server is the source of truth. Clients predict ahead and roll back when the server disagrees.
- Single-player is a match too: the machine runs the server itself and connects to it through a loopback transport, so there's no separate offline path. The engine assumes nothing about what games do with matches (no built-in pause): it gives them the tools.
- There's one kind of match, so no special case for playing alone: a match starts closed, and whether other machines can join it is a switch on it (`Session.Open` and `Session.Close`), not another way to start one. Single-player is a match nobody else was let into.
- Clients have no input delay: they run ahead of the server by about half the round trip plus a small margin, so their inputs arrive in time, and only other players' inputs are guessed. The server says how early their inputs arrive, and clients adjust their lead by it. A client that sends none (a game without an input) ignores it and keeps the lead it joined with.
- Matches go over WebRTC data channels, unordered and unreliable, on the web and on desktop alike, so web and desktop players meet in the same rooms: they're the only way a browser can reach another player's machine directly, so browsers host matches as well as join them. Desktop hosts also take players on a UDP port, our own thin layer, which `Session.Connect` reaches by address. The protocol above the transport stays the same.
- Desktop WebRTC is our own (`platform/src/rtc/`): P-256, ChaCha20-Poly1305 and the hashes, ICE with STUN and TURN, DTLS 1.2 and SCTP, only as much of each as a data channel needs, written from the RFCs with no third-party code, so games carry no license terms for it. Browsers are its check: it has to work against Chrome's and Firefox's (`platform/tests/rooms.mjs`). Desktop games reach the relay at `wss://` with the system's TLS (`src/rtc/tls.c`): SChannel on Windows (`secur32`), Secure Transport on macOS (the Security framework), and OpenSSL's libssl on Linux, loaded at run time rather than linked, so nothing ships with games; without it, Linux games can't reach the relay. Browsers hide their local address behind `.local` names, which desktop games don't look up (hearing mDNS answers means listening on port 5353, which Windows' firewall asks players about): browsers' checks still reach the desktop side, which learns their address from them.
- Direct connections come first, since they cost the relay nothing. Players find each other in rooms, by a code the host picks itself (`Session.room`), so there's nothing to wait for; a code already taken gets another before anyone could read it. The relay we host (`relay/`) introduces players in a room, passing along what WebRTC needs to connect them, and nothing else goes through it. Players whose networks can't connect directly go through Cloudflare's TURN: the relay makes short-lived credentials with the key in its Fly secrets, and hands them to players. Dedicated servers stay.
- How it works now (`tide/session.h`): the server ticks the one true world and sends each player every tick: who joined or left, the inputs that changed, and a hash of the world after it. Inputs that didn't change or arrive keep the last one, on every machine. A client keeps a snapshot of every tick from the last one the server confirmed (the verified world) to the one it predicted. A tick that arrives as the client guessed only has its hash checked against its snapshot; one that went otherwise runs on the snapshot before it, and the ticks after it run again. Worlds go as deltas (`tide/delta.h`), each a numbered transfer in chunks. A region that goes is XOR'd byte by byte with the one a stride before it where that packs it shorter: the writer tries none, 1, 2, 4, 8 and the size of the region's rows or cells, counting the bytes each leaves that aren't zeros in a sample of it, 8 at a time, and the region says which. Joining players get the world, and a cookie that gets them their `PlayerID` back when they join again. The server keeps every tick since a world it sent until that player catches up, however long the world took to arrive (`keep_needed`); a player that falls behind otherwise gets the world again. A player with a world to build it from (its own, when its hash differs; its last one, coming back to a match that changed hands; or, joining, the match as it started, which it starts itself when starting calls no C: `tide_game.pure_start`) gets the hashes of the server's pages first, after how the match started, says which its world lacks, and gets those; one that doesn't come out as the hash says is asked for again, whole. Worlds that go in one update anyway go whole. Inputs go as what changed (`write_input_delta`): in frames, from the slot's input as the world keeps it before the tick; from players, each from the tick before. In an input, ints, int enums, players and entities go as varints in bits (7 bits a group and a bit for whether more follow, `tide_bits_put_varint`), signed ones zig-zagged first, so small numbers take a byte; floats keep their 32 bits, and byte and ushort enums their 8 and 16. As a delta, an int or int enum that changed goes as by how much (`tide_bits_put_changed_difference`, wrapping), and a float as its bits' XOR with what it was, the run of bits that differ and where it starts (`tide_bits_put_changed_xor`, as Gorilla packs floats), or its own 32 bits where that's shorter. Packing never changes a value: every one comes back bit for bit, NaNs and -0 too, and `tests/test_bits.c` checks it. Datagrams keep times to 16 bits and small numbers as varints, and a tick where nothing happened is its hash and a byte. `net_a_match_costs_little_to_keep_going` pins what a match costs to keep going: a change that makes it cost more updates the test on purpose. A client sets its clock from the server's tick as it sent the world, not the world's own tick, which a transfer leaves behind. Everything is resent until acknowledged; nothing waits on a reliable stream. A machine that runs the server and stops for a while (a breakpoint, a browser that freezes the page) stops its server and its player with it: its session drops the time beyond what the server can run in one update, so the two never time each other out and nothing runs ahead to catch up. A client of another machine keeps to the real time.
- Host migration is a game's choice, off by default: the `hostMigration` setting (see `docs/spec.md`, Sessions). When a room's host leaves or times out, another player's machine goes on from its verified world, which is bit for bit the server's at that tick, and the others join it again with their cookies. The server sends its players a handover record (`MSG_HANDOVER` in `engine/src/session.c`): its room's code and key, its own player, whether it's open, and who's in the match with their cookies' SHA-256. The relay decides who hosts (`{migrate: code, key}`, in `relay/relay.mjs`): it pings the room's host, and gives the room to the first player there when the host is gone. `tide/host.h` drives it (`tide_run_migrate`), with `tide_platform_room_migrate` on both platforms. A goodbye can be lost, so a match that ends (`Session.End()`, or its last scene) also tells its transports (`tide_transport.end`), and a room tells the relay (`{end}`), which keeps it as ended for five minutes: a player who comes back to take it over hears it ended. The room keeps its relay connection (or makes one) until it's said, and asks for the room first on one that hadn't, since the relay may not know it yet: a room's code shows before the relay hears of it, and a host that lost the relay is reaching it again. Nothing about it is timed on the server. So in a match with host migration on, the server keeps nothing beside the world that the players don't also have: what it keeps of its own (each player's cookie, as a hash, and whether the match is open) goes to every player. A feature that keeps more on the server has to send it too, or not work in those matches. Private scenes the new host wasn't in are lost, which is the game's to know; a match on an address (no relay to meet at again) ends as it does today.
- Sync relies on determinism as much as possible. The main thing sent over the network is inputs.
- Inputs come from clients, so they're attack points. The engine is forgiving with them and makes bad values hard to turn into broken math or a broken game: NaN and infinite floats in an input become the field's default before the game's `Sanitize` runs, and math functions avoid spreading NaN where they can (`Math.Clamp` always returns a value in range; `Math.Min` and `Math.Max` with one NaN return the other argument).
- State corrections are supported. Divergence is detected through state hashing.
- Clients can be denied specific state through a visibility system, for example other players' cards in a poker game.
- Visibility is dynamic. The server decides at runtime what each player can see, through an API.
- Each client tracks a **verified tick**. It is the latest tick for which any state the client lacked but should have has arrived, and any divergence has been corrected by the server. Ticks after it are predicted and may be wrong for a while.
- Game code can tell verified state from predicted state. For example, a player death visual can wait until the death is verified.
- Secrets such as RNG seeds are ordinary state behind visibility, for example an entity the client can't see. They need no special mechanism.
- Clients don't have to simulate the whole world. LOD borders and culling are resolved through state sync.
- Hosting (not built yet): Tide will host games for people, and hosted matches will run as WebAssembly in a sandbox (a runtime like wasmtime), with a time budget per tick. Owning the language doesn't make hosted code safe by itself: games can call C, and even pure Tide can loop forever. In the sandbox, C only reaches the game's own memory and what the host gives it, so `extern` stays allowed. A hosted game's match code, and the C it calls, has to build for the web; a server build can leave out views and local code.

## Determinism

Given the same build and the same inputs, simulation results must be bit-identical on every supported platform.

### Floats

- Only the IEEE 754 basic operations (`+ - * /` and `sqrt`) can be trusted to give identical results across platforms. Build everything else from them.
- No FMA contraction. The compiler must never fuse `a*b + c` into a single instruction.
- No fast-math. No reassociation or reordering of float operations.
- Simulation code must not use the platform math library (`sin`, `cos`, `atan2`, `exp`, `pow`, and so on). Use the engine's own math library, which is built only from the basic operations.
- Vector math (vectors, matrices, quaternions) is written in-house: it only needs the basic operations, and third-party vector libraries often use approximate instructions or the platform math library.
- Transcendental functions may come from a third-party library, but only as source vendored into the engine and compiled with its flags. Prefer correctly rounded implementations, such as CORE-MATH: they return the same bits on every platform by definition.
- No approximate instructions such as `rsqrtps` or `rcpps`. Their results differ between Intel and AMD.
- Denormals stay enabled (no FTZ/DAZ) on every thread and every platform. WebAssembly can't flush denormals, so no other platform may either.
- No relaxed SIMD on the web: its fused multiply-add gives different results on different machines.
- No x87 floating point.
- NaN in simulation state is a bug. NaN bit patterns are not portable.

### Parallelism

- Running in parallel must never change results. Thread timing must not decide the order of anything observable. That includes system order, command playback, reductions, and entity ID allocation.

### Systems that touch the same data

- It is not an error for two systems to write the same component. It's normal.
- Those systems run one after the other, in a deterministic order.
- Tooling tells the user why they didn't run in parallel. Example: "`MoveSystem` runs after `GravitySystem`: both write `Position`."
- Two systems conflict when one writes a component or singleton the other reads or writes, unless they can never touch the same entity: the compiler proves that from the archetypes (`with Player` against `with Enemy`). Two systems that change the match's text or lists conflict too, as they share its heap. `Spawn`, `Add`, `Remove`, `Destroy` and `Send` never conflict, because they're recorded and applied at the end of the tick in order. Event handlers run then too, as each event's turn comes, so they aren't part of the tick's schedule. Input and `Time` are only read.
- Conflicting systems keep their order in the tick, and `[Before]`/`[After]` order systems too. A system starts as soon as everything it waits for is done; there are no barriers between stages. A system's stage is only how deep it is in that chain.
- A system splitting its entities across threads is the other kind of parallelism, and it doesn't change results either.
- The tick runs on threads (`tide/jobs.h`): the schedule (`analyze_parallelism` in `compiler/src/parallel.c`) becomes a task graph, a task per system, or per chunk for a system that splits its entities. The platform layer has the threads (`tide_platform_jobs`, one per core); sessions take them in their desc and pass them to `tide_game.tick`. Each task records into a queue of its own, merged in the order one thread would have recorded it. A tick with little work runs on one thread: tidec reckons each system's cost per entity, and threads only start past about a tenth of a millisecond's work (three on the web). A thread with nothing to do spins briefly, then yields its core (`tide_yield`): with a thread on every core, one the system pushed aside would otherwise hold the tick up for a time slice. Web pages run on threads when they're cross-origin isolated (see Web builds). `platform/tests/jobs.tide` checks threads against one thread, tick by tick, natively and under Node.
- Besides components and singletons, systems wait for each other over what's the whole match's: changing text or lists (its heap; reading it alongside is safe, as the heap's page table is read atomically and replaced ones are freed once systems are done, `tide_heap_settle`), and spawning by a system that runs on one thread (entity IDs are handed out in order, and it hands them out as it runs). C is trusted and counts for neither. A system only splits its entities across threads when it changes no text, list, grid or singleton (`system_splits`).
- A parallel loop (`parallel (var at in cells by 2 offset o)`, and a foreach over a grid whose steps only touch their own cell, `own_cell_only` in `compiler/src/check.c`) runs inside its system, a fork and join (`tide_parallel_for`): its steps go to a function of their own after the system's, with what they read of the code around them copied into a struct, and the pool's threads that have nothing else to do help (`help_loop` in `engine/src/jobs.c`); outside a threaded tick, or for a small loop, the system's thread runs them alone. A tick with a system that has one runs on threads. Its tasks are tiles, the blocks that start in one chunk's place (`tide_par_tile`): every place a sized grid's blocks start in, or for a grid with an open axis, the places of the chunks it has and of those before them whose blocks get into them, where a block that takes in none of its chunks is skipped (`tide_par_live`). A step writes into a copy of its chunk (`tide_par_buffer`, made with a compare-and-swap, the first one's for all), and reads the grid itself, which doesn't change while the steps run; the loop's end puts the copies into the grid in chunk order (`tide_par_end`). A foreach over a grid that goes in order goes row by row (`tide_grid_rows`), over a grid with an open axis through the chunks it has, sorted, in the scratch area (`tide_scratch_memory`, which takes its own memory when the area has no room, freed with the area's mark).
- A system that splits and spawns gives temporary handles (`TIDE_ENTITY_TEMPORARY` in the generation, with its task's number; `tide_new_entity`). Once its tasks are done, it settles them (`tide_settled`): its entities get IDs in the order one thread would have given them, and its tasks' queues (`tide_settle_item`) and the entity fields of its `mut` components (`tide_settle_<system>`) get the real handles. Settling keeps the tick's order among spawning systems (each settles after the one before it that spawns is done) and comes before anything waiting for the system starts, so the IDs are the same as on one thread. Systems look entities up while one makes them, so the entity table's page table is read atomically like the heap's (`tide_entities_settle`). Text shows a temporary handle as `Entity(new)`, and C tells with `tide_entity_is_temporary`.
- The language server shows each system's stage and waits above it and on hover, and `tidec --schedule` (or the `<game>_schedule` build target) prints it as text for CI and agents. `compiler/tests/schedule/` pins its output.
- Declared access that isn't used is a warning, since it makes other systems wait for nothing: a `mut` parameter that's never written, or a parameter that's never used (a component only needed as a filter belongs in `with`). The language server offers quick fixes, as it does for adding a missing `mut`.
